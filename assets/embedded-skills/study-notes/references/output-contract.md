# Output Contract

最终输出不要暴露“我选了哪条路由”，除非用户明确追问。路由是内部判断，不是用户必须看到的元信息。

## Global rules

- 结构跟着 `route + complexity + study_goal` 走，不跟着固定模板走；`study_goal` 的调制规则见 [study-goals.md](./study-goals.md)（路由定骨架，目标最多追加一个专属块）
- 标题可以朴素，不必强制使用 emoji
- 如果用了 emoji，只允许一段一个，且必须和内容语义相关
- 类比不是全局硬要求；精确性更重要时，用场景、原句、数字代替
- 可信度提醒只在会影响理解或使用时出现

## Fact anchor policy

- 原文直说的内容可以直接写。
- 从原文推出来的判断，用“从这段看”“看起来”“这暗示”等语气标出。
- 常识补充或背景解释，用“通常”“一般来说”等语气标出。
- 不要把例子、个案、作者判断写成普遍事实。

## Low-confidence output

- 文本不足时，不写完整笔记，要求调用方提供已提取正文。
- raw image 或 binary 没有 OCR/转写时，返回 `modality_mismatch`。
- 路由低置信但层次清楚时，先拆 mixed-content；目标不清时按最可能目标产出，结尾用一行标注所采假设，不追问。

## Language policy

- 用户指定语言时，按用户语言输出。
- 用户未指定时，默认跟随用户请求语言。
- 跨语言材料用用户偏好语言输出，专有名词和关键术语保留原文，首次出现时给简短解释。

## Analogy policy

- 类比不是全局硬要求。它服务于"理解"层的图式搭建（见 [study-goals.md](./study-goals.md)），所以最适合教程、框架、抽象概念；越靠近事实与数字（新闻、数据、条款），越应该用场景、原句、数字代替。
- 各路由的具体策略以对应 method 文件的 `## Analogy policy` 小节为准，这里不再重复。

如果你发现自己在给每个关键点硬塞一个类比，说明你已经偏离了这份 skill 的目标。

## Shared output building blocks

根据情况从下面选择，不要求每次全用：

- `这是什么/发生了什么`
- `核心点/核心发现`
- `怎么做/怎么用`
- `论点与理由`
- `故事主线与转折`
- `5W1H`
- `边界/限制/未知项`
- `值得记住的`
- `一句话总结`

## Complexity-specific shape

### `short`

建议 2-3 段：

1. 一句话说明主题或事件
2. 1-3 个关键点
3. 需要时补一句“为什么这值得记住”

### `standard`

建议 3-5 段：

1. 主题或主线
2. 路由对应的核心主体
3. 应用/影响/反驳空间/转折/限制
4. 可选的可信度提醒
5. 一句话总结

### `layered`

建议三层：

1. `一屏总览`
   - 3-5 句说清主题、最大结论、怎么用
2. `分层摘要`
   - 按章节、论点群、数据群或阶段来拆
3. `记忆和使用层`
   - 该记什么
   - 该怎么用
   - 还缺什么信息

## Credibility reminder

以下情况优先加入 `可信度提醒` 或 `还不能下结论的地方`：

- 新闻还在发展中
- 评论主要靠作者判断，没有充分证据
- 数据报告样本、口径、时间范围有限
- 教程或方法论说得很绝对，但没有说明适用边界

写法要求：

- 用短句
- 明确区分“原文说了什么”和“这件事目前能不能完全信”
- 不要端着“审判口气”

## Optional continuity and processing note

- 只有上游提供 `prior_notes` 时，才加“与已有笔记的关系”。
- 发生路由覆盖时，必须附一行最简 `处理说明`（说明按正文形态而非表面格式整理，不暴露内部路由名）。
- 完整的 route、confidence、主要依据和被舍弃的备选，只在用户问“为什么这么拆”“详细分析”“推理过程”时展开。

## Route-specific minimums

- `knowledge-tutorial`
  - 至少说清楚“这是什么”和“怎么用”
- `opinion-commentary`
  - 至少说清楚“作者主张”“作者凭什么这么说”“哪里还可以再想一步”
- `narrative-story`
  - 至少保留“起因-冲突/转折-落点”
- `data-report`
  - 至少保留“结论-关键数字-边界”
- `news-brief`
  - 至少保留 `5W1H` 和“哪些还没确定”
- `framework-methodology`
  - 至少保留“框架是什么、由什么组成、怎么配合、何时适用”
- `mixed-content`
  - 至少把不同层拆开写
- `unsuitable-input`
  - 先说明为什么不适合普通笔记，再给替代格式

## Final check

提交前问自己：

1. 读者看完后，能不能快速恢复原文的“骨架”？
2. 这份笔记会不会把原文本来很重要的精度、时间、边界弄丢？
3. 我是不是把本来不该类比的内容写成了比喻练习？
4. 如果删掉所有小标题，笔记本身还顺吗？
5. 这份笔记像是在帮助学习，还是像在机械套模板？
