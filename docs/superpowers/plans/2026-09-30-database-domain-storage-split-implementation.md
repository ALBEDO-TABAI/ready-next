## 1. 完成标准与范围

- 总管理器只负责数据库打开、可用性检查、迁移/初始化、关闭及领域存储组装，不再承载产品读写方法。
- RSS、日历、浏览器、聊天、设置、远程频道分别有唯一 SQL 所有者。
- 所有存储共享同一个数据库连接及事务；关闭后不能残留旧连接或自行重开。
- 数据库路径、表结构、迁移顺序、SQL 参数、空值语义、默认值和返回结果保持不变。不迁移用户数据、不新建数据库、不引入 ORM。
- 更新实际调用方、测试和类型依赖；删除旧的总管理器产品方法，不留下两套路由或动态方法代理。
- 用真实 Electron SQLite 验证多域读写、事务、关闭/重开、已读收藏分类、日历重复事件、聊天/频道及设置；针对旧行为的回归与类型检查通过后，才恢复 RSS 功能改版。

## 2. 根因与目标结构

现有 `repositories/*` 多数是产品调用适配层，最终转发到 `DatabaseManager`。它们统一了一些调用签名，却没有将 SQL 职责从总管理器移出。继续往其中加分类、正文、事件和日报会扩大跨域耦合。

目标调用链：

```text
产品服务 / 已有 Repository（命名、异步和业务配置适配）
    → DatabaseManager 的具名领域存储
        → database/{rss,calendar,browser,chat,settings,channel}-store.ts
            → 同一个 DatabaseConnection
```

保留已有 Repository 的产品接口是为了不改变 IPC、配置序列化、异步接口等职责；不是保留旧 SQL 实现。SQL 只在领域 Store 中存在。原 `DatabaseManager.getRSSItems()` 等入口一次切换为 `DatabaseManager.rss.getRSSItems()`，不增加旧名转发、反射代理或继承混入。

| 归属 | 负责 | 不负责 |
|---|---|---|
| `database.ts` | 原生依赖、连接、迁移、初始化、关闭；组装六个存储 | 产品 SQL、模型、采集、界面状态 |
| `database/connection.ts` | 连接类型、连接获取合同、连接不可用错误/断言 | 打开第二个连接、全局实例 |
| `database/records.ts` | 当前领域数据记录类型的唯一声明 | SQL、生命周期、隐式类型转换 |
| `database/rss-store.ts` | 来源、文章、底稿、分类统计、分析任务 | 采集、模型整理、报告生成 |
| `database/calendar-store.ts` | 日历、事件、重复规则展开、导入与覆盖记录 | 独立调度、网络同步 |
| `database/browser-store.ts` | 书签、历史、下载记录、浏览器任务 | 操作原生网页或下载器 |
| `database/chat-store.ts` | 会话、消息、附件索引、召回同步、反问清扫 | 启动 Agent、发送外部消息 |
| `database/settings-store.ts` | 原始设置键值读写 | AI 配置解释与迁移（仍由 AppSettingsRepository 负责） |
| `database/channel-store.ts` | 远程频道、线程和收件事件记录 | 网络连接、外部发送、鉴权决策 |

领域 Store 由连接获取函数构造，每次操作取得所属管理器的当前连接，不缓存裸连接、不拥有 close。该函数用于六个真实存储及测试隔离，不设计可插拔数据库框架。既有单例/初始化顺序不变；本合同针对主资料库六域，搜索 worker 原有独立连接保持原边界。

连接类型与领域记录移出，消费者直接引用新权威声明；不让纯类型读取依赖 Electron/native 加载。日历内部行类型与解码 helper 留在日历 Store，领域特定 helper 不进入通用连接文件。

后续 RSS 改版的保存边界：

- 来源、文章正文和分类结果仍由 RSS 域负责；其内部可以按职责拆文件，但继续共用主连接与事务。界面、Agent、导出通过同一保存与读取入口，不各自持有可写副本。

- 若需恢复升级前资料，先完全退出 Ready，保全当前 `ready.db` 及存在的 `ready.db-wal`、`ready.db-shm`；使用对应迁移前备份替换数据库，移开原库的 WAL/SHM，再使用与备份结构相匹配的代码启动。不得把旧备份与新库的日志文件混用，也不得让旧代码直接读取不兼容的新结构。恢复会撤销备份之后的资料变化，执行前须明确恢复时点。
- 存储验收必须覆盖旧库升级、失败回滚、已读/收藏保留及重启读回；通过后才把新的 RSS 功能接到这个保存入口。保存检查通过不代表智能分类、事件归组或日报已经完成。

## 7. 继续 RSS 前的结果保存与恢复方案

### 7.1 本轮复审发现

本节记录施工前发现及目标合同；当前实施结果见 §8。前述测试数字是历史验收记录，不替代本节行为验证。

当前 `rss-processing-store.ts` 的 `enqueue` 遇到同一输入版本的历史任务时会跳过自动处理；`publish` 保存当前分类和成功状态。`rss-organization-store.ts` 的 `applyDerived` 会覆盖同一文章与分类的旧自动判断。因此，文章正文 A 已整理、改为 B 再整理、最后恢复 A 时，历史任务虽然存在，当前分类仍可能是 B 的过期结果。事件保留了旧证据，但当前关联也没有因此恢复。问题在于把“曾执行过”当成了“当前结果已可用”。

需要分清三种保存职责，继续使用同一主数据库和事务，不再拆物理数据库，也不引入新调度器：

| 保存内容 | 唯一职责 | 禁止行为 |
|---|---|---|
| 执行记录 | 请求、输入版本、开始/结束、费用计数及失败/未知状态 | 凭 success 状态推断结果仍存在或仍适用 |
| 已接受的整理结果 | 保存特定文章版本、规则版本和方法版本对应的实际判断与依据 | 保存一份原模型命令，日后重复执行创建事件 |
| 当前关联和用户纠正 | 指向适用于当前版本的已存结果；手工决定独立覆盖自动结果 | 用过期自动结果覆盖手工决定，或让不同入口各存一份可写判断 |

### 7.2 拟定保存结构与消费者切换

1. 在 RSS 域内增加不可变的已接受结果记录，绑定任务、文章版本、方法版本及各分类规则版本。保存实际接受的判断、理由与依据，明确区分“不属于”和“信息不足”。任务记录只关联结果，不再额外存一份可独立修改的结果正文。
2. 当前分类关系保留人工决定，并指向适用的已接受判断。界面、筛选、Agent、统计和导出统一通过此关系读取。迁移后删除旧的自动判断正文读写路径，不能长期双写旧字段与新结果表。
3. 事件结果引用已经接受的证据身份、关系和理由；事件及事实归属从当前保存的关联读取。恢复时只重新绑定有效证据，不能重放模型的“新建事件/新增进展”操作。“信息不足、无事件”同样是可保存和恢复的有效结果。
4. 发布时在一个事务内完成结果保存、当前关联更新和任务成功；恢复时在一个事务内完成适用性检查、当前关联更新和查询版本更新。任一步失败均不暴露半份结果。通知在事务提交后发出。
5. 只有文章版本、分类规则及方法一致、结果确实存在时才允许复用。任务执行记录不参与替代判断。已撤回证据不可恢复；当前手工分类和归组优先保留。事件被合并后沿证据的现有归属恢复，不能复活旧事件。

这里是目标结构，施工时先以行为测试固定结果身份和唯一性约束，再确定最小表与索引。只为本次真实版本恢复需求保存必要历史，不建设通用事件溯源框架。

### 7.3 迁移与旧资料保护

- 职责拆分本身仍无需数据迁移；本节结果保存调整需要新增迁移。编号按施工时实际序列确定，并接入现有升级前一致备份。
- 当前仍有完整判断及依据的记录可以迁移，保留其真实来源、文章和规则版本；无法证明方法或执行归属的历史记录不得伪造为可复用模型结果。
- 旧成功任务已被后续版本覆盖、无法找回实际结果时，明确返回“历史结果不可恢复”。既不把 B 的结果当作 A，也不自动重新付费。用户仍可显式选择重新整理。
- 保留订阅、正文、已读、收藏、人工决定及任务历史。升级失败完整回滚，禁止删库重建；恢复旧备份按 §5 执行。
- 删除文章、分类定义或撤回证据时，核对结果、当前关联和任务历史的引用规则；不能留下可被查询误用的悬空结果。无需为尚未实现的日报预建空表。

### 7.4 先保存后功能的施工顺序

| 顺序 | 工作 | 完成出口 |
|---|---|---|
| D0 | 固定当前工作树与失败反例，区分已提交保存代码和未提交事件实现 | 原生临时库能重复证明 A→B→A 缺口；不改用户库 |
| D1 | 增加结果保存和迁移，切换当前关系及全部读取方 | 无双写、无旧自动结果读取路径；旧资料可升级并重开 |
| D2 | 接通恢复、手工优先和事务失败处理 | 下表全部行为通过，重复恢复不新增模型调用或事件身份 |
| D3 | 验证共享存储、查询与真实窗口，再更新完成状态 | 保存出口通过后才恢复 RSS；未通过项不能由历史绿色结果代替 |

| 合同 | 必须观察到的结果 |

|---|---|---|

分页还有一项设计约束：普通 SQLite `rowid` 会在删除末行后复用。仅保存首读 `max(rowid)` 不能保证后续新增记录不进入旧页，因此不得将它作为固定资料范围的唯一凭据。

### 9.3 职责边界与写入顺序

**启动和读取分开。** 分析管理器提供明确的启动恢复入口，由 RSS 启动所有者在接纳新分析任务之前调用；同一连接生命周期只执行一次。开发重绑、查看列表、Agent 读取和任务进度查询不得重复恢复，也不得把本轮新任务判作上次中断。初始化完成标志只能在恢复成功后设置。读取仍可显示失败、未知和历史状态，但不触发分析、网络或付费重算。

**任务记录与报告文件分开管理。** 现有 RSS Store 保存任务状态、来源版本和报告发布身份；分析管理器负责生成和发布；文件读取只消费已经发布的身份。优先使用现有 `meta_json` 中一份明确的报告字段，保存任务 ID、固定报告文件名、内容 SHA-256、字节数和发布时间；路径仍以任务的 `output_dir` 为准，不另存可独立改写的路径副本。各消费者从同一报告字段读取，不各自首读时“认领”文件。

所有新任务使用 `root/<analysis-kind>/<jobId>/`。文案与视觉流程共用这一目录规则；暂停后继续仍属于原任务，但不得由目录层数猜测资源根目录。源视频等可复用输入沿已有输入复用机制读取，报告、字幕及其他可覆盖产物写进任务目录。没有发布身份的旧暂停任务在恢复时先分配独立输出目录，再执行；不得继续覆写旧共享目录。

发布顺序固定为：完成临时文件 → 原子替换任务内的最终文件 → 读取并验证最终字节 → 在同一次数据库更新中写入报告身份与成功状态 → 提交后通知。文件写成而数据库更新失败时，文件只是未发布产物，不能展示为成功报告；不自动补发模型任务。该顺序不宣称文件系统和 SQLite 具有共同事务。

**报告读取不推测归属。** 入口仅接受任务 ID 和分页位置；从成功任务的发布身份定位固定报告文件，校验真实路径仍在任务目录内、文件身份与发布身份一致。续读必须绑定该身份；读取前后核对任务未删除、仍成功且发布身份未变。报告被外部修改或替换时返回明确不可用原因，不能默默读新版。源文章删除与任务删除分别判断：任务仍保存时可读取有效报告并标注来源已不存在；任务已删时不能凭残留文件继续读取。

旧成功任务没有发布身份时，仍可读取真实任务记录，但不能把当前路径中的文件认作当年的报告。尤其共享目录内可能已覆盖的文件，不得通过首次计算哈希补造历史归属。保留旧文件与路径信息，明确说明无法核验，不自动重新生成、不伪造恢复成功。

**完整分页采用明确的版本边界。** 首期沿用现有 RSS 查询版本机制：游标绑定目录种类、规范化筛选、排序、首读版本和最后位置；续页在同一读取事务内核对版本与读取数据。补齐所读表的新增、修改、删除对版本的更新，包含来源、定义、分析任务、历史判断和事件证据。版本变化时明确要求重新开始，不能追加到旧页；不以 `rowid` 上界或时间戳假装完整快照。不新建一份目录资料副本。

落实时将目录失效版本保存在同一 `rss_workspace_state.catalog_revision`：单向跟随原资讯版本，分析任务进度及目录额外字段只推动目录版本。这样不会因为后台进度更新而反复作废普通资讯列表。它只是读取一致性标记，不保存任何资料副本；不可把外部文件或采集诊断内存当成受此版本约束的数据库快照。

此选择简单但有取舍：任务频繁更新会使遍历重新开始。验收须测量实际影响；若无法完成合理规模遍历，先修订此合同并验证更窄的版本范围，再交付。不得静默放宽一致性。完整目录包括停用来源、历史方法与内容版本、撤回证据和信息不足结果，并将“当前仍适用”“人工覆盖”作为明确字段；可变筛选也受同一版本约束。

## 10. 整轮复审发现的方法版本与媒体读取缺口

`aaad3936` 复审发现：恢复入口会拒绝旧方法，但普通分类查询、事件组卡和日报仍可能消费已经绑定的旧方法结果。另有视频校正文稿、结构化转录及媒体路径仅写入 manifest，专用 RSS 读取入口未消费。前面的分项通过不关闭这两项。

方法版本修复采用共享有效性条件，不再由每个消费者重判：人工决定优先；自动分类须同时匹配内容、规则及当前方法；明确的 `origin=legacy` 原分类保持既定迁移语义，`origin=model` 且方法未知的结果只能作为历史。自动事件也须匹配当前方法；手工归属保留，但原文变化仍需显示提示。历史依据保留可读，候选必须标明历史状态。

机器验收：旧方法和未知模型方法在列表筛选、元数据、统计、日报入选/待整理数量及旧刊 needsUpdate 中保持一致；人工覆盖仍可生效，取消后不能露出有效的旧自动结果。旧事件不再合并当前卡片，历史事实和手工纠正仍可读。新增迁移只推进查询版本以使升级前的查询引用失效，不重写原文、结果、报告或阅读状态；备份失败阻止升级。

媒体后续修复须将已有产物按受控种类绑定到发布时的文件身份：报告、校正文稿、结构化转录可分段读取；媒体仅返回实际引用和已核验的存在/缺失状态，不声称已理解画面。读取沿同一专用校验器，不信任未经绑定的旧 manifest，不放开通用文件权限。旧产物无法核验时明确说明；不自动补下载、转录或重新调用模型。具体写入/读取范围及失败反例在实施前补齐。

### 10.2 已有媒体产物的发布与读取合同

- 报告继续由 `reportArtifact` 独占身份；同一任务的 `analysisAssets` 只保存补充产物，种类限定为校正文稿、结构化转录、网页输入快照、场景评分和源视频，不重复保存报告或另建通用资源库。所有文本共用原有文件范围、哈希及版本分页校验。
- 生产流程直接返回实际产物路径给发布者，不把未绑定的 manifest 重新解释为权威。文本产物限于本任务目录；复用的视频允许位于该任务已经保存的素材根目录内。文本保存后读回计算身份，视频只登记文件的路径、大小及系统文件身份；成功状态、报告身份和补充产物身份同一次写入。
- 文本角色若已生成却无法核验，任务不得宣称发布成功。视频可能未被下载或已被外部移走，分别记录未保存、缺失或已变化；其读取结果明确“仅检查本地文件身份，未读取/理解视频内容”，不对大型二进制作同步全量读取。旧任务没有补充产物身份时标明不可核验，不追读其 manifest 补造历史。
- 新增 RSS 专用只读工具按任务和受控种类读取；目录一次列出有限角色，长文本按版本续读，删除任务、改动文件、目录越界、缺少版本均不得读取旧结果。现有 RSS 本机授权和只读地板贯穿到实际 SDK 调用，不增加通用文件权限。
- 原文链接、封面与 URL 类型提示继续由已有保存字段派生。界面使用同一个纯转换方法显示封面，HTTP(S) 以外的引用不加载；Agent 得到明确的类型提示、远端可用性尚未核验及未进行媒体理解的边界。封面显示失败只作客户端提示，不伪造成服务端已验证结果。
- 验收覆盖三条真实生产流程、每种已生成文本读到尾部、旧 manifest 不获信任、复用视频的存在/删除/变更、越界拒绝、发布失败不留下可用身份，以及实际视频卡片/阅读面封面和既有报告功能回归。不调用外部下载或付费模型来补缺失资料。
