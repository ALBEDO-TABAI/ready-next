# Ready Next W3 资料库模型与文档：文件是正本，对象是界面，索引是底座

属于 [收束路线图](2026-11-11-ready-next-coherence-roadmap.md) 的 W3，落实 E3、E4。证据：[c-document](../audits/2026-11-11-ready-next-coherence-audit/c-document.md) 与实机观察 O2、O3、O7、O8、O13、O14。依赖 [W2](2026-11-11-ready-next-w2-shell-unification-implementation.md) 的侧栏槽位与 [W1](2026-11-11-ready-next-w1-design-system-implementation.md) 的基元。

## 1. Notion 式还是 Obsidian 式

用户的问题是：Notion 让人忘记文件在哪，只管信息的层级；Obsidian 让人留意文件怎么放，强调人与知识索引。Ready 该选哪个？

答案是它们不在同一层，不需要选。

| 层 | 采用 | 理由 |
| --- | --- | --- |
| 存储 | Obsidian 式：Markdown 文件与文件夹是正本 | 内容能离开 Ready；助手、Codex、别的编辑器、git 都能直接读写。在 Agent 时代，开放的文件是优势，封闭的块数据库是负担。这是整合计划的 D1，已经实现 |
| 界面 | Notion 式：用户面对的是页面、数据库、画板、书，按层级组织 | Ready 要的是心流。想的是“那页会议笔记”，不是“`项目/新书发布/会议 11-03.md`”。这是 D5，界面已移植 |
| 底座 | 索引：全文、关系、身份 | “不用管文件在哪”要靠它才成立：`⌘K` 找得到，关联面板连得上，助手读得到，改名搬家不断链 |

所以 Ready 的说法是：**在资料库里，你想的是页面；文件一直在那里，需要时翻开看。** 资料库之外的文件夹不归 Ready 管理，如实当文件看。

现在的毛病不在模型，在界面把两层同时摆了出来：左边一棵文件树，旁边一棵页面树。

关于 RAG，有一个事实要说清：**现在没有向量检索。** 检索是 SQLite FTS5（中日韩双字切分，BM25 排序）加关系索引；助手靠只读工具按需读取。旧 Ready 所谓“md 与 RAG”里的后一半，目前就是全文检索加助手的多步查找。是否补向量检索见 M9。

## 2. 模型条文 M1–M10

| 编号 | 条文 |
| --- | --- |
| M1 正本 | 页面、画板、来源页、书、附件以文件为正本（D1 不变）。界面状态可以从文件与 `ready.db` 重建 |
| M2 对象 | 资料库里的一级概念是对象：页面、数据库、画板、书、来源页、其他文件。界面显示标题与图标，不显示扩展名和路径；类型名用中文 |
| M3 一棵树，两种视角 | 资料库只有一棵树。**页面视角**（默认）合并 `A.md` 与 `A/`，隐藏 `.assets` 与 `.ready`，非 Markdown 文件显示在它所在的层级；**文件视角**显示磁盘上的真实结构。在树的顶部切换，按资料库记住。别处不再有第二棵树 |
| M4 挂载的文件夹 | 资料库之外的文件夹单列在“文件夹”一节，只有文件视角。在那里不支持的能力（页面头部、数据库、评论、同步块）界面上不出现入口。提供“收进资料库”：把文件或文件夹移入资料库，从此按页面管理 |
| M5 标题 | 显示的标题取 frontmatter 的 `title`，没有就取文件名。正文第一个一级标题如果与标题相同，页面视角不再重复显示它（只是不渲染，不改文件）。Ready 新建的页面不再往正文里写 `# 标题`。导入的 Markdown 原样保留 |
| M6 数据库是一种页面 | 数据库有明确的新建入口。行就是页面。树上数据库用自己的图标；行默认不在树上列出（在数据库里看），文件视角下照常显示 |
| M7 系统对象不进页面树 | 书房的 `阅读.md`、模板目录等由专门入口承载的对象，不在页面树里重复出现 |
| M8 索引不是界面 | 索引的消费者是 `⌘K`、关联面板、文件涌现、助手工具。用户界面里不出现“索引”这个词，除了“设置 › 资料库”里的状态与重建 |
| M9 语义检索先量再建 | 先建一个检索评测集，量现在的全文检索够不够。第二类或第三类低于 70% 就做本地向量索引（方案见 §5，已定），作为可重建的派生索引（服从 C5）；达标就不做。没有数据之前不引入 |
| M10 助手的视角 | 助手按对象读（M7-A/B 的只读工具），按两个写入口写（D4），产出带出处（`ready_source`）。这部分不变 |

## 5. 检索

- **评测集（M9）。** 在测试资料库里建 30 条查询：10 条原词能命中的，10 条要同义或改写才能命中的，10 条中英混合或跨语言的。每条标出应命中的对象。指标是前五条里有没有正确答案。
- **判断。** 第一类应接近全中。第二类或第三类任一低于 70%，就做 T9；都达标就不做，并把结果记在本文。
- **不达标时的方案（已定，路线图 §9）。**
  - 本地嵌入模型，资料库内容不上传。模型不进安装包，在“设置 › 资料库”里启用语义检索时下载，可删除。
  - 选型在动手时用同一个评测集比较，条件是：支持中、英、日；体积约 150MB 以内；能在 Node 或 WebAssembly 里运行；许可证允许随应用分发。不预先写死型号。
  - 按现有的块区间切分页面与来源页；向量存在 userData 下的派生库里，不进资料库目录；随文档索引增量更新；删掉可以全量重建。
  - 数据量在十万块以内时用内存里的逐一比对，不引入向量数据库或 SQLite 原生扩展；超过再评估。
  - 查询时与全文检索的结果按名次融合。消费者是助手的资料库检索工具、`⌘K` 里排在精确匹配之后的“相关”一组、关联面板的“相近的页面”。
  - 验收：同一评测集第二、三类不低于 85%，第一类不退步；一千页的测试库首次建索引的时间和占用记录在案。达不到就不发布这项能力。
- **`⌘K` 的显示**（标题、中文类型、对象覆盖）在 W6 做；本工作线只负责评测集和它的脚本。

## 8. 风险

| 风险 | 处理 |
| --- | --- |
| 合并两个侧栏时，文件树与页面树的选中、展开、拖拽状态各有一套 | 以页面服务的树为数据来源，文件视角只是另一种投影；拖拽统一走 W6 的 `x-ready-ref` |
| 隐藏正文的同名一级标题会影响块定位、大纲、锚点 | 只在渲染层跳过，区间与锚点仍按源码计算；大纲里也不重复列出；有专门的往返测试 |
| 数据库行不在树上，用户找不到行页面 | `⌘K` 能搜到；数据库里点开；文件视角可见 |
| 用户习惯了外层文件面板的缩略图视图 | 文件视角保留缩略图视图 |
