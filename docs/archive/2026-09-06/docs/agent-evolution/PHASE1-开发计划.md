## 2. 波次排布（关键约束：I3 与 T4 共享 tool-executor.ts，全局串行）

```
波次 1（全并行，零相互依赖）
  X4 注入账单        ← 先有账单，后续所有注入改动可量化
  X1a 任务索引 v1
  X3 资产 loader
  K1 信念卡存储
  T5 ready-debug     ← 文档单，随时可做
  T4-1 映射表        ← 纯新增不接线，不碰 tool-executor

波次 2（依赖波次 1）
  K2 DB 镜像（K1 后）
  B2 纪律资产（X3 后）
  B3 站点卡（K1 后）
  I3-1 闸门（开始占用 tool-executor.ts ——自此 I3/T4 串行）

波次 3（串行尾）
  T4-2 信封试点（I3-1 合入后改 tool-executor）
  I3-2 冻结放行（T4-2 后；含 migration + IPC 最小闭环，本阶段最大单）

波次 4
  G1 收口（verify 链、CLAUDE/AGENTS 同步、08 表回填）
```

预期节奏：波次 1 可由多执行者并行消化；波次 2-3 的 tool-executor 串行段是关键路径。若单执行者（Codex 逐单施工），建议顺序：X4 → X1a → X3 → K1 → T4-1 → T5 → K2 → B2 → B3 → I3-1 → T4-2 → I3-2 → G1。

## 3. 开关与灰度

| 开关 | 默认 | 说明 |
|------|------|------|
| 任务索引注入 | 开（与旧日志并行注入一个版本） | 出问题回退 = 关索引段，旧链路未动 |
| 确认闸门 | 开（M4 全放行；**M2+M3 同等走确认卡**，预批准阶段一不实现；清单从最保守子集起步：删除/批量移动/对外发送） | 清单扩充走合同修订，不走代码即兴；预批准待阶段二 I-auth 能力就绪 |
| 工具信封 | 开（additive，无消费方时零影响） | — |
| 站点卡注入 | 开（仅 5 个种子域名命中才注入） | — |
| 知识卡体系 | 工具暴露开；**注入链路本阶段不存在**（K3 属阶段二），无需开关 | — |

## 4. 风险登记

| 风险 | 盯防点 | 应对 |
|------|--------|------|
| tool-executor.ts 串行段拥堵 | 波次 2-3 排期 | I3-1/T4-2/I3-2 三单提前写好失败测试，减少占用窗口 |
| 确认卡与 ask_user_questions 单 pending 约束冲突 | I3-2 测试"第二个 M2 被拒" | 已写进合同测试；若实测打架，降级方案 = M2 第二动作直接结构化拒绝（不排队） |
| 同步阻塞确认占用 run（"原 run 内等待"模型） | I3-2 超时 10 分钟 + run 抢占/取消即 expired | 合同已定二选一为「原 run 内等待」、绝不跨上下文补执行；放行经 release 入口仍跑 authorization（不提权） |
| 阶段一 M3 无预批准 = 高频确认打扰 | 观察确认卡触发频率 | 接受为阶段一代价；对象级预批准能力 I-auth 列阶段二，就绪后接 M3 预批准路径 |
| browser-site-experience-store 模块名/接口与设计称呼不符 | B3 第一步定位核对 | 合同已注明"以 HEAD 为准"；接口差异大则 B3 拆出 spike 半单 |
| X1a 索引行泄漏他谱系任务 | 谱系过滤复用 C4.3 函数而非重写 | 合同已锁定复用；测试含他谱系断言 |
| 资产打包路径 dev/prod 不一致 | X3 双解析测试 | 沿用 assets/skills 既有模式，不发明新路径逻辑 |
| pending_confirmations 表与未来 Q1（阶段二扩列）字段重叠 | I3-2 审计行 TODO 标注 | 确认事件迁 proof_refs 在阶段二 Q1 合同内列明，本阶段只写 metrics |

## 5. 阶段完成定义

1. 13 单全部合入，`npm run verify:evolution-p1`、`npm run verify:native`（K2/I3-2 含 SQLite 迁移）与全量 `typecheck + test` 绿；
2. 08 表本阶段行回填为"已合入"；
3. 人工验收三件事：① 随便一轮对话能在 metrics 看到 context_bill；② 让 agent 删一个文件会弹结构化确认卡、确认后参数未变地执行；③ 浏览器任务的提示词里能看到纪律资产与（命中时）站点卡；
4. 阶段二合同（K3-K4/K6 启动接线/Q 系列/C 系列/X1b/X2/I1-I2/**I-auth 对象级动作授权**/T1-T3/E1-E2/B1 spike）开题评审。

> **新增阶段二工单 I-auth**（Codex 评审 P1#1 衍生）：把"用户对某对象批准了某动作"做成可证明的结构化事实（不是从粗粒度 TurnFrame 意图推断），就绪后 M3 的"预批准有效"路径才接上。在此之前 M2/M3 一律走确认卡——这是阶段一确认闸门安全性的前提，不可因体验打折提前放开。
