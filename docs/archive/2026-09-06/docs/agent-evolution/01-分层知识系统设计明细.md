## 1. 目标与现状差距

**目标结构**（Matrix 三层模型的 ready 化）：

```
RULES.md            身份/策略/操作指令 —— 每会话注入（决策契约）
knowledge/index.md  一行一卡的检索线索目录 —— 每会话注入（知道"有什么、何时读"）
knowledge/{slug}.md 原子信念卡 —— 索引命中才按需读取（知识本体）
```

**ready 现状**（取证）：

| 能力 | 现状 | 评价 |
|------|------|------|
| 分层注入框架 | `prompt-assembly.ts` L0(6000字符)/L1(8000)/L2(6000) 三层预算已存在 | ✅ 直接复用 |
| 身份文件 | SOUL.md（人设，DB+file 双轨）+ MEMORY.md + AGENTS.md + TOOLS.md 分散在 `.ready-agent-memory/` | ⚠️ 缺统一 RULES 层，行为规则散在 4 个文件 |
| 知识存储 | `agent_knowledge`(k/v 表) + `docs/*.md`（领域规则片段，L2 trigger 加载） | ⚠️ 非原子、无置信度、无图谱、无索引 |
| 检索 | `agent_triggers` 关键词触发 + session_recall 256 维哈希向量 | ⚠️ trigger 是关键词制；无"索引线索"这一层 |
| 生命周期 | `MemoryLifecycleManager` 6h 归档（按时间，L1 30d / L2 90d+访问数<3） | ⚠️ 只有时间衰减，无去重、无置信度、无索引重建 |
| 用户画像 | `user_profiles` 表 + USER.md | ✅ 已有，按 userId |

**核心差距**：缺"索引即检索线索"这一中间层，缺原子卡 + 置信度 + 图谱链接，缺从使用信号反馈的维护（03 篇负责维护，本篇负责数据模型与注入）。

## 2. 目标文件布局（两级分形，为 04 篇专项 agent 预留）

```
.ready-agent-memory/
├── RULES.md                      # 全局：身份基调、跨 agent 公共规则（取代 MEMORY.md+AGENTS.md 的行为部分）
├── USER.md                       # 保留现状（用户画像，跨 agent 共享）
├── TOOLS.md                      # 保留现状
├── knowledge/                    # 全局知识（所有 agent 共享）
│   ├── index.md                  # 维护任务重建；每会话注入
│   └── {slug}.md                 # 原子信念卡
├── agents/{agentName}/           # 专项 agent 作用域（04 篇启用；第一阶段可只有主 agent）
│   ├── RULES.md                  # 该 agent 的身份/策略/操作指令（取代 SOUL.md 的扩展位）
│   └── knowledge/
│       ├── index.md
│       └── {slug}.md             # 含 routing-*.md 路由卡（主 agent 专属）
└── memory/{YYYY-MM-DD}.md        # 保留现状（当日日志，C4.3 已限域）
```

设计决策：

1. **文件为真值源，DB 为索引缓存**。卡片是 markdown 文件（用户可直接看和改，与 Matrix 一致、与 ready 现有 `.ready-agent-memory` 习惯一致）；`agent_memory_metadata` 表中以 `category='belief'` 镜像一行（字段映射见 §4），用于访问计数、UI 列表与向量检索。维护任务（03 篇）负责"从磁盘真值重建 DB 索引"，方向永远是 file → DB，冲突时文件赢。
2. **两级作用域**：全局 knowledge 服务所有 agent；`agents/{name}/knowledge` 服务单个 agent。归属原则照抄 Matrix："信息住在它的受众住的地方"——服务单 agent 的事实进 agent 卡，服务全局的进全局卡。
3. **SOUL.md 不动**：人设（语气、角色描述）继续走 `agent_personalities`；RULES.md 承载的是"策略与操作指令"（何时做什么、禁止什么），与人设分离。两者都进 L0。

## 3. 信念卡与索引格式规格

### 3.1 卡片 frontmatter（照搬 Matrix，微调 tag 枚举）

```yaml
---
title: 一句话标题
description: 一行摘要（index 线索的来源）
confidence: H | M | L            # 默认 M
tag: knowledge | self | preference | aspire
created: 2026-06-11
source: 一行来源（run id / 会话标题 / 用户原话）
---
正文自由 markdown。用 [[slug]] 链接其他卡。
```

- tag 语义：`knowledge`=外部事实/技术/领域知识；`self`=该 agent 如何工作（含主 agent 的 `routing-*` 路由卡）；`preference`=用户在该域的偏好（区别于 USER.md 的全局画像）；`aspire`=开放问题/涌现候选（03 篇用）。
- slug 即文件名（kebab-case）。`## Backlinks` 区块由维护任务用 `<!-- backlinks:auto -->` 标记管理，agent 与用户不手写。
- PII 纪律照抄 Matrix：凭证/敏感标识绝不入卡（ready 已有 `secret-storage.ts` 专门放敏感数据，继续用它）；用户要求代用的公开账号进 USER.md。

### 3.2 index.md 格式

```markdown
# Knowledge Index（或 # {agentName} Knowledge Index）

## self
- [[routing-video-tasks]] — Read before 路由视频剪辑类请求 [H]

## knowledge
- [[xiaohongshu-collection-limits]] — Use when 采集小红书（脚本检测风险与限速） [H]

## preference
- [[doc-rewrite-style]] — Applies to 文档改写任务的语气与格式偏好 [M]

---
Updated: 2026-06-11T10:00:00Z
```

规则（照搬 Matrix crystallize §3c）：按 tag 分组、组内置信度降序、空组省略、`Updated:` 必须存在；**描述写成行动触发句**（"Read before… / Use when… / Applies to…"），不是被动摘要——这一行的唯一使命是让 agent 知道"什么时候该读这张卡"。

### 3.3 卡片状态机（闭合规格）

每张卡 frontmatter 必带 `status`，全生命周期五态：

```
staged（待确认）──用户采纳/二次信号/用户明示──► active（已生效）
   │                                            │
   ├─ 用户驳回 ──► rejected（被拒，保留 30 天供撤回，后删除）
   ├─ 14 天无晋升信号 ──► 直接删除（expired，不留尸体）
   │                                            │
   └────────── frontmatter 解析失败 ──► invalid（损坏）◄┘
```

| 状态 | 进 index 注入 | UI 呈现 | 清理规则 |
|------|--------------|---------|---------|
| staged | **否** | 记忆面板"待确认"区 | 14 天无信号删除 |
| active | 是 | 正常列表 | 走 03 篇衰减（先降档后删除） |
| rejected | 否 | "已驳回"折叠区 | 30 天后物理删除 |
| invalid | 否 | "格式损坏待修复"标记 | 永不自动删除（用户资产），修复后重新解析 |

规则：状态迁移**只有四个写入点**——memory_write_card（初始 staged 或用户明示 active）、用户 UI 操作（采纳/驳回）、维护任务（二次信号晋升/过期清理）、文件 watcher（解析失败标 invalid / 修复后回归）。每条迁移写审计行。验收测试：五态各迁移路径 + "staged 不出现在任何注入内容"断言。

## 4. 数据库改造（最小增量）

复用 `agent_memory_metadata`，新增/复用字段映射：

| 卡片字段 | DB 字段 | 备注 |
|---------|---------|------|
| slug | `id`（或新增 `slug` 列） | 与文件名一致 |
| title/description | `title`/`summary` | 已有 |
| tag | `category`（值：`belief:knowledge` 等或新增 `tag` 列） | 已有 category |
| confidence | `priority`（H=100/M=50/L=10）或新增 `confidence` 列 | 建议新增列，语义更清晰 |
| 作用域 | `scope_id` → 复用为 agent 作用域（`global` / `agent:{name}`） | 已有 |
| 访问信号 | `access_count` + `agent_memory_access_log.was_useful` | 已有，03 篇维护用 |

新增迁移（一张表都不加，只加列）：`agent_memory_metadata` 增加 `slug TEXT`、`confidence TEXT`、`file_path TEXT`、`status TEXT`（§3.3 五态）、`content_hash TEXT`（§7 同步校验用）。卡 `status` 的 DB 镜像与文件 frontmatter 以文件为准（§7 规则）。向量检索复用 `session_recall_vectors` 的 256 维哈希方案，为卡片建向量（新增 `kind='belief'` 维度或复用 content_hash 机制）作为索引线索之外的兜底召回。

## 5. 注入与读取链路改造

### 5.1 注入（改 `prompt-assembly.ts`）

| 层 | 现状 | 改造 |
|----|------|------|
| L0 | SOUL+USER+MEMORY+AGENTS+TOOLS | + `loadRULES(agentScope)`：全局 RULES.md + `agents/{name}/RULES.md`，置于 SOUL 之后；MEMORY/AGENTS 中的行为规则逐步迁入 RULES（过渡期共存，见 §7） |
| L1 | 会话摘要 + 当日日志 | 不动（C4.3 限域已覆盖） |
| **L1.5（新）** | 无 | `loadKnowledgeIndex(agentScope)`：注入全局 + agent 两份 index.md 的正文（预算 1500 字符，超出截断低置信度行） |
| L2 | trigger 规则 | 保留；trigger 可引用卡 slug（`agent_trigger_refs` 已支持），命中时直接注入卡全文 |

注入位置建议在 L1 之后、L2 之前，作为独立 section（`<knowledge-index>` 包裹），并附一句固定指令（照搬 Matrix 行为约束）：

> "当索引行与当前请求、目标文件、工具对象、路由决策或进行中任务相关时，先读对应卡片再行动；无关条目忽略。"

### 5.2 按需读取（工具面）

新增两个轻量工具（注册进现有 memory_* 工具族，所有 domain 默认可见）：

- `memory_read_card { slug, scope? }` → 返回卡片全文（带 frontmatter）。实现 = 路径守卫下的文件读取（写入白名单两 glob：普通卡 `.ready-agent-memory/**/knowledge/*.md`、站点卡 `.ready-agent-memory/**/knowledge/sites/*.md`；`sites/` 是唯一允许的 knowledge 子目录，供 11 篇站点卡使用）。
- `memory_write_card { slug, scope, frontmatter, body }` → 写/更新卡片（原子写：tmp + rename），同步 upsert DB 镜像行。**这是 agent 实时写入通道**——对应 Matrix"可记的东西当轮落盘"原则；02 篇的 learningDecision=memory-card 也走它。

不给 agent 开放通用文件写入到记忆目录——守卫住路径与格式（frontmatter 校验，malformed 即拒绝并返回原因），坏卡进不了系统。

## 6. 检索纪律（写进 RULES.md 的默认内容）

全局 RULES.md 初始版本要包含三条（这是 Matrix workspace-schema 的精髓，成本最低收益最高）：

1. 索引命中必读卡：匹配当前请求/文件/工具/路由的索引行，先 `memory_read_card` 再做实质工作；
2. 当轮落盘：出现值得长期记住的事实/偏好/教训时，当轮用 `memory_write_card` 写卡（带至少一个 `[[slug]]` 前向链接，没有合适目标就链到主题 MOC 卡），不要"留到以后"；
3. 归属裁决：服务单个专项 agent 的写进该 agent 作用域，服务全局的写全局；用户个人画像类进 USER.md 不开卡。

## 7. 真值源迁移边界（架构级变更声明，须单独立合同）

⚠️ "文件为真值源、DB 为索引缓存"对 ready 是**真值源方向反转**（现状是 DB 优先、文件 fallback，见 loadSOUL/loadUSER 的双轨逻辑）。这不是小迁移，落地前必须把以下边界写进实施合同：

1. **谁赢**：仅 belief 卡与 RULES.md 适用"文件赢"；SOUL（人设）/user_profiles/触发规则**维持 DB 优先现状不动**——反转范围严格限定在新增的知识层，存量记忆体系零改动。
2. **同步方向与时机**：file → DB 单向；三个同步点——`memory_write_card` 写入时同步 upsert；文件 watcher（复用 document-engine 的 additive listener 模式）捕捉用户手改后增量同步；维护任务（03 篇）每轮全量校验重建。DB 行带 `content_hash`，哈希不一致以文件重算。
3. **用户手改的处理**：手改后 frontmatter 仍合法 → 正常同步；frontmatter 损坏 → DB 镜像行标 `invalid`，**不注入、不删除**，记忆面板显示"格式损坏待修复"（坏卡可见但无害）；手改与 agent 写入竞态 → 文件系统层 mtime 后写赢（卡片是单文件原子写，无半态）。
4. **UI 改造边界**：记忆面板增加"知识卡"页签（列表来自 DB 镜像，编辑跳转文件）；现有 L0/L1/L2 记忆管理 UI 不动。
5. **回滚开关**：`knowledge_system_enabled` 设置项；关闭 = 停止注入与工具暴露，文件保留——回滚无损。
6. **迁移路径**：不删旧文件；MEMORY.md / AGENTS.md / docs/*.md 保持加载，新 RULES.md 以"增量"身份注入；迁移期由维护任务逐步把 docs/*.md 稳定规则原子化为卡片，人工确认后从旧文件移除；`agent_knowledge` k/v 存量数据一次性导出为卡片（脚本 + 人工过目）。

## 7b. 预算与协同

1. **DEFAULT_FILES 硬编码兜底**（prompt-assembly.ts:124-168）增加 RULES.md 与空 index.md 的默认内容，保证全新安装可用。
2. **token 预算**：L0 预算 6000 字符不变，RULES 全局+agent 合计目标 ≤2000 字符（策略写卡、RULES 只留契约）；index 1500 字符 ≈ 25~35 行，超出按置信度截断并在尾部标注"另有 N 条低置信度条目"。
3. **与 C4.3（记忆注入限域）协同**：知识索引按 agent 作用域加载，天然不存在跨任务祈使句污染；卡片正文只有按需读取才进上下文。
4. **隔离区协同**（03 篇 §2 修订）：`status: staged` 的新卡**不进 index 注入**，仅维护任务确认/用户采纳后晋升——实时落盘不丢观察，注入门槛防污染。
