# Tag Forge 低干预打标与打包版闭环合同

## 根因证据

1. 旧技能和词表强制每份文档只写一个工作流状态，首次固定为 `待整理`；完成判定又把“至少一个 active 标签”当成充分条件，所以三份文档只写 `待整理` 仍被报告为完成。
2. 模型最初提出了有效内容标签，但 `tags` 调用与实际 schema 不一致；准备工具又把绝对路径返回模型，路径脱敏后变成不可回传的 `~/...`，导致后续写入被判为批次外路径。
3. 存疑标签的问题、卡片 id 和审核结果曾依赖模型在多个工具之间转述；部分 provider 只保留文本，结构化数据在桥接中丢失，因此确认流程不可能稳定完成。
4. 写回、打开 tab 同步、索引回读和标签归属原本不是同一个可回滚单元，后续任一步失败都可能留下“文件已改，任务却失败”的半完成状态。
5. 旧批次只要看到任意标签就跳过文档，所以只有 `待整理` 的历史错误不会被后续修复；读取失败和超过固定深度的 Markdown 还可能被静默漏掉，却返回 `done: true`。
6. `waiting_review` 曾可以被记为成功进度并产生 proof；同一轮因此可同时出现“打标完成”和“本轮未完成”。
7. 新文档曾允许省略标签提案并把稀疏结果当成完成，标签依据也没有绑定最终落盘正文；正文保存成功时，缺少形态或主题标签仍可能被误报为完成。
8. 文本工具桥只把 prepare 的简短摘要交给下一模型回合，完整 `itemId`、正文和词表被丢弃；同时固定 4 回合上限会在多页批次仍有 `remaining` 时伪报完成。
9. 词表曾让 `教学`、`收藏`、`胡迪尼` 同时归属两个 facet；带 facet 的模型提案看似可消歧，但无 facet 的已有手工标签会被另一套解析顺序误判，甚至把内容标签迁成工作流状态。

## 完成条件

1. `tags` 只存内容语义，Tag Forge 本轮自动负责的标签必须恰好一个 form，并至少一个 domain 或 entity，安全范围为 2–15 个；用户手工或导入标签原样保留，不占自动标签名额，也不转为自动标签或全局词表项。除 form 最多一个外，domain/entity/use 不设独立硬配额；模型按“直接证据、跨文档复用、独立检索路径”决定保留，同义词、翻译和拼写变体只留一个归一标签。active 标签名与别名必须跨词条唯一，标准名优先解析，冲突词表在加载时拒绝。当前文档已有且能由受控词表标签或别名确定 facet 的手工标签，直接在本文件内满足覆盖要求，不依赖模型本轮重复提案；正文证据成立的同名手工标签也只在本文件内满足覆盖，不进入全局词表或反问。两者都不重复写入、不重复询问。工作流状态单独写入 `ready_state`，不在文档预览中显示。
2. 模型只提交带 `evidenceExcerpt` 的结构化提案。已有标签和别名立即归一；置信度不低于 0.92、文内证据直接出现标签名的新 domain/entity/use，只受单文档 15 个自动内容标签安全上限约束并直接采用；容量溢出直接忽略，不交给用户确认。只有真正存疑的项交给用户。
3. 模型只调用 prepare/apply，并只回传不透露主机路径的 `itemId`。typed folder reference 只授权这两个打标动作，不扩大其他文件工具权限；授权只认 Renderer 附在用户消息上的结构化文件夹元数据，本轮实际引用的历史文件夹复用同一元数据且不带入未引用附件，不解析正文中伪造的文件夹标记。执行前以真实路径拒绝符号链接越界；目录内 Markdown 符号链接只登记失败，不读取目标正文，合法的符号链接工作区根仍可正常使用。文本工具桥必须把 prepare 的完整结构数据交给下一模型回合，并沿既有任务回合预算循环到 `done:true`。确定项全部写完后，宿主把整个文件夹的存疑项合并到 Agent 反问；文档中已存在的用户标签不进入反问，同一 folder run 最多一张、最多 35 项，超出容量的低置信候选直接忽略，不制造第二张卡或无卡等待状态。答复后自动执行审核与原批次续跑。
4. 存疑提案使用精确 proposal id，并绑定 batch/item/scope/run/card；不同批次的同名标签不得互相覆盖，同一卡片重放必须幂等，用户忽略的项在原文档重试时不得再次弹出。
5. 批次状态使用原子持久化。策略版本变化时重建旧批次；深层 Markdown 必须全部扫描，无法读取的文档必须显式留为失败并阻断完成。只有状态标签或不满足新内容覆盖的文档自动进入修复。
6. 文件、当前 tab、索引和数据库归属必须全部写入且回读一致才返回成功；任一步失败恢复原文与旧索引，不留半完成文件。
7. `waiting_review`、`done:false`、running 和 pending 都是非终态，不产生完成证明，不得让聊天结果、任务卡与实际终态互相矛盾。
8. 现有三份错误文档必须用正式打标路径修复，磁盘与当前 Ready 索引回读一致；全新重扫必须返回 0 份待处理、0 个错误。
9. 新文档的每条标签证据必须来自最终将落盘的正文；最终正文、回执 hash、写回标签和索引回读必须一致。系统自动标签缺少“恰好一个 form + 至少一个 domain 或 entity”时不得稀疏完成，正文可以保留，但同一回执必须可重试补全标签；用户已有标签始终保留。
10. 显式 `@[tag-forge]` 和模型自动 `use_skill(tag-forge)` 必须在同一轮收敛到相同的 5 个必要工具；自动选技不得遗留通用文件工具或技能自行追问入口。

## 验证入口

- `npm run verify:tag-forge`
- `node scripts/run-file-emergence-native-tests.cjs`
- `npm run verify:native`
- `npm run typecheck`
- `npm run build`
- 真实文件批次写回、索引回读与新鲜重扫
- 真实 Ready 文档预览的标签与内部状态可见性检查
- 新 DMG 的签名、完整性、挂载内容和安装包内技能合同检查

## 非目标

- 不开放通用 shell 或任意文件写入。
- 不删除用户手工标签，不自动批准新 form 或工作流状态。
- 不用宽松的文本模糊匹配代替模型语义判断；代码只负责证据、文档上限、状态、权限与一致性。
