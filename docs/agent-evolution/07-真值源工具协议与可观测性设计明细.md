## 1. 账本所有权矩阵（P9 根治）

### 1.1 问题本质

同一 run 在 run_meta / task_projections / skill_task_runs 三处各自为政（取证案例：run_meta 记 `research/60`，projection budget 记 `short_task/24/used=0`；被 kill 的 run 在 run_meta 永远 `working`）。Matrix 的答案不是合并表，而是**所有权与写方向**："Ordinary departments maintain source facts; the dashboard refreshes from them" + "malformed records are ignored"。

### 1.2 所有权矩阵（设计的核心交付物）

| 账本 | 所有的事实 | 唯一写入者 | 别人怎么用 |
|------|-----------|-----------|-----------|
| `run_meta` | **run 级**：终态/initiator/terminal_reason/时长/token | run-finalizer（C1.1 已强制） | 只读 |
| `task_projections` | **task 级**：状态/步骤/Criteria/Proof/CheckIn（02 篇）/预算视图 | task-projection-sync + finalizer（CheckIn）+ 登记的 UI 点 | UI 只读消费；06 篇任务索引从此生成 |
| `browser_tasks` | **采集执行级**：进度/游标/单项结果 | browser-engine | 终态只通过 C2.1 事件桥上行为 proof，**不直接改 projection** |
| `skill_task_runs` | **技能执行级**：子进程状态/产物路径 | skills-runtime | 同上 |
| `run_state.json` | **进程间续跑句柄** | skill 子进程 | finalize 时收割，不作为 task 状态源 |

写方向铁律：**执行级账本 → 事件 → task 级账本 → run 级账本**，永远单向上行；下行只有"创建任务/下发参数"。任何模块直接跨级写（如 browser-engine 直接改 projection status）都是违规——用 CI gate 锁死（仿 finalize-funnel：`check-ledger-write-direction.cjs`，按 repository 调用点白名单扫描）。

### 1.3 一致性策略

- **budget/task_type 等冗余字段**：指定 task_projections 为口径源，run_meta 的对应列降级为"收口快照"（finalize 时从 projection 抄录，永不独立更新）——消灭"两处各记各的"；
- **malformed ignored + 告警**：消费端（UI 投影、任务索引、维护回合）遇到字段非法的行：跳过 + 记一条 `ledger_malformed` metric，**不带病显示也不崩溃**；维护回合（03 篇）汇总告警供人工处理。

## 2. Reconcile 泛化（P8 残余 + 与 C1.3 的关系）

C1.3（S1-5 工单）做启动 reconcile 处理三类 stale 行，本设计是其**泛化与周期化**：

1. **启动时**（C1.3 范围）：所有 `status ∈ {working, running, background_running}` 的行 → 存活性核对（pid 存在？run 在内存登记？事件桥有挂起事件？）→ 死行通过 **finalizer 通道**关闭：CheckIn(blocked, blockerCategory: external_system_failure 或 module_waiting, nextAction: "进程重启中断，可续跑")——收尸也走唯一闸门，不开旁路；
2. **周期性**（新增，挂在 03 篇维护调度上，纯代码无 LLM）：每轮维护前跑一次轻量 reconcile，捕捉启动后泄漏的孤儿行（守护进程崩溃、事件丢失）；
3. **续跑友好**：被收尸的行保留 continuation_ref，用户下次进入时经 06 篇任务索引可见、可一键续跑（对接 C5.1 懒恢复）。

⚠️ **写方向迁移边界（这不是简单泛化）**：当前 S1-5 的启动 reconcile **直接改多张表**——这在当时是合法实现，但与本篇"终态只经 finalizer/adjudicator 通道"的写方向相抵触。T3 实质是改变 reconcile 的账本写入方向，迁移须分三步：① 新增 reconcile 专用 outcome（`initiator: 'reconcile'`，CheckIn 由 adjudicator 组装），与旧直接写路径**并行运行一个版本**，对账日志比对两路结果一致；② 一致性确认后切换为新通道单跑；③ 旧直接写路径删除，并把 reconcile 写入点纳入 check-ledger-write-direction gate 白名单收口。每步独立可回滚。

Matrix 对应物：merge-user-md 的僵尸锁回收（kill -0 探测持有者存活）——"每轮从真值重建派生态、僵尸持有者直接回收"的同一哲学。

## 3. 工具输出协议对齐（D-tool1）

### 3.1 现状与目标

ready 已有工具错误契约（errorKind 元数据，2026-04-22 合同），缺的是 **kind 按"下一步谁来做什么"设计** + hint 字段。对齐 integrations-do 信封：

```typescript
interface ToolResultEnvelope {
  ok: boolean
  kind: 'ok' | 'arg_error' | 'auth_expired' | 'rate_limited'
      | 'not_found' | 'upstream_error' | 'network_error'
      | 'denied_by_policy' | 'denied_by_user_negation'   // 05 篇两类拦截
      | 'internal_error'
  data?: unknown
  error?: { message: string; hint?: string; retryAfterSec?: number }
  meta?: { elapsedMs: number; cacheState?: string }
}
```

kind → 行动语义表（写进工具开发规范 + 注入给模型的工具使用说明）：

| kind | 模型该做什么 | 运行时已做什么 |
|------|------------|---------------|
| arg_error | 重读参数 schema 修正后重试 | 无重试 |
| auth_expired | 停止重试，引导用户到设置/登录 | 无重试 |
| rate_limited | **勿再试**，告知用户稍后或问是否排队 | 已按 retryAfter 退避重试 ≤2 次 |
| upstream/network | 报告 + 提供替代路径 | 5xx/网络已退避重试 ≤2 次 |
| denied_by_* | 改道或向用户澄清 | 拦截即终态 |

**迁移步骤（现状是 `text/data/errorKind` 体系，改造范围大，分四步渐进）**：
1. **映射表先行**：`errorKind → kind` 的静态映射函数 + 单测穷举（未知 errorKind → internal_error + 告警），不动任何工具；
2. **信封并存**：ToolExecutionOutput 增加 `envelope` 字段（新结构），旧 `text/data/errorKind` 字段原样保留——**UI 与现有消费方零改动**，新消费方（模型注入的工具结果渲染、X4 账单）读 envelope；
3. **试点先迁**：首批只迁两域——browser 工具（错误形态最丰富）+ skills 子进程结果（stdout 信封纪律同步落地），观察一个版本；
4. **逐域跟进 + 旧字段冻结**：全部域迁完后旧字段标记 deprecated（只读兼容，不再新增取值），最终退场另立工单。

### 3.2 重试策略分级（运行时层统一实现）

429 尊重 Retry-After + 指数退避 ≤2 次；5xx/网络退避 ≤2 次；401/403 **零重试**；arg_error 零重试。当前各工具域自行其是的重试逻辑收敛到 tool-executor 公共层（与 C5.2 的 provider 级重试分工：C5.2 管模型 API，本节管工具内的外部调用）。

### 3.3 技能子进程输出纪律

stdout 恰好一个 JSON 信封（READY_SKILL_RESULT_PATH 机制保持），诊断一律 stderr——杜绝子进程日志污染结果解析（Matrix integrations-do 的 stdout/stderr 二分纪律）。

## 4. ready-debug 自诊断技能（P10）

**使用者分两类，入口分别设计（不混）**：

| 使用者 | 入口 | 范围 |
|--------|------|------|
| 外部编码代理（Claude Code / Codex / Cursor），**v1 唯一目标** | 仓库内 `.claude/skills/ready-debug/SKILL.md`（Claude Code 自动发现；其他代理用 README 指路复制粘贴，仿 MatrixUserDebugSkill 的分发方式） | 开发/排障场景，可读源码与日志 |
| 应用内自诊断（最终用户），**v2 可选** | 嵌入式技能 + 设置页"诊断报告"按钮，纯诊断与上报、不改代码 | 打包环境，仅日志与 DB 巡检 |

v1 技能正文预置四张表：

### 4.1 预置内容（技能正文的四张表）

1. **日志源优先级表**：`ready-database.log`（DB/ABI 问题首查）→ `ready-directchat.log` + `ready-agent-metrics.log`（agent 行为）→ `ready-tools.log`（工具层）→ `ready-browser.log`（采集）；路径均在 `<tmpdir>`，附定位命令；
2. **症状 → 检查映射表**："设置丢失/历史空白/scope not found" → 先查 ready-database.log 的 NODE_MODULE_VERSION 错误（附检查脚本：`node -e` 比对 Electron ABI 与 better-sqlite3 编译目标），**不要先怀疑前端状态**；"无声死亡" → run_meta 查 working 孤儿行 + context_bill 看最后注入；"重复确认/不确认" → action-confirmation-policy 表与 negation 字段；
3. **数据巡检 SQL 包**：三账本一致性抽查（同 run 的 run_meta vs projection 口径比对）、working 孤儿行清单、malformed 行清单；
4. **findings.md 五段式模板**：症状 / 可能原因 / 证据（日志行引用）/ 临时绕过 / 修复尝试。

### 4.2 修复门

发现可修复问题时先问用户"现在修，还是只出报告？"——修复动作有显式同意门（移植 MatrixUserDebugSkill 的 code-change gate）。
