## 1. 问题定义

04 篇解决了"这件事归谁"（路由与派生），但没有定义"一件大事如何变成多件可验收的小事再合回来"。Matrix 真正的执行管线是：

```
下行：Task packet + 精选上下文引用 + 期望产出
上行：结果摘要 + 产物引用 + 未决问题
包体：Brief / Trigger / Criteria / Context Refs / Next Action / Proof Refs / Check-ins
```

ready 已有零件：`task_projections` 的 `parent_task_id`/`parent_step_id`/`steps_json`（C4.2a 计划持久化）、SubAgent 框架、后台任务（browser/skill）。缺的是把它们串起来的**合同**：包的结构、分派纪律、验收归属、汇总规则。

## 2. 任务包（TaskPacket）规格

任务包不另立表——它是 `task_projections` 的一种用法约定。标记方式**定死为新增列 `packet_role TEXT NULL`**（`'parent' | 'child'`，普通任务为 NULL）：不复用 `module`（module 语义是执行域 system/skill/browser，包不是执行域），不用布尔位（parent/child 需要区分）。UI、统计、DomainAdapter、测试一律以 `packet_role` 为唯一判定。复用 02 篇的四列：

| 包字段 | 载体 | 说明 |
|--------|------|------|
| Brief | task_title + task_summary | **用户原话相关片段逐字保留**（05 篇最小传话）+ 本包目标一句话 |
| Owner | agent_id（04 篇冗余列） | 哪个 agent 作用域负责；执行席位（SubAgent/后台任务）不是 owner |
| Criteria | criteria_json（02 篇） | 本包"做完"的判据，分派时**编译期写定**，不留给执行方自定义 |
| Context Refs | 新增 context_refs_json | 文件路径 / 卡片 slug / 父包 id——**只传引用不传转述**；执行方按需读取 |
| Expected Output | criteria 内的产出项 | 期望产物形态（文件/回答/数据），落点路径约定 |
| Proof / Check-in | proof_refs_json / checkins_json（02 篇） | 包级验收，裁决层（02 task-adjudicator）统一执行 |
| 预算份额 | budget_json | 从父任务预算切分，防单包吃光全局预算 |

层级约束：**最多两层**（父包 → 子包），禁止递归嵌套——单用户桌面场景不需要 Matrix 的多级部门树，两层覆盖"研究+采集+成文"类复合任务已足够；更深的需求说明该拆成多个顶层任务。

## 3. 分派编译器（Dispatch Compiler）

### 3.1 定位

编译器是主/专项 agent 在**规划步骤**里的一个受约束动作，不是新服务。输入 = 用户请求 + 当前 agent 的知识索引；输出 = 包树（写入 projections）。提示词资产化（06 X3：`prompts/dispatch/compile-packets.md`）。

### 3.2 编译纪律（写进提示词资产 + 代码校验）

1. **触发门槛**：仅 `multi_step_task` 与 `research` 类型默认进入编译；`direct_answer`/`short_task` 永不分包（一包都嫌多）；
2. **一包一交付物**："每个包恰好一个可验收交付物"——包的 Criteria 里必须有产出项，没有产出的"协调包"非法；
3. **编译期定验收**：Criteria 在分派时写死（执行方可补 not_applicable 说明，不可改写判据本身）——验收权与执行权分离；
4. **上下文最小化**：Context Refs 只放执行该包必需的引用；禁止把父任务全文或当天摘要塞进子包；
5. **执行通道选择**（代码查表，不是模型决定）：

| 包特征 | 通道 |
|--------|------|
| 同 agent、需要对话上下文 | 当前会话内顺序执行（steps_json 推进） |
| 同 agent、独立可并行/长跑 | SubAgent（verbatim brief 注入） |
| 浏览器采集/技能长任务 | 后台任务（browser_tasks/skill_task_runs），完成经 C2.1 事件桥回包 |

### 3.3 汇总包（Aggregation）

父包自身是一个汇总包，其 Criteria 固定模板：

```
- c1: 所有子包均已 Check-in（completed / 显式降级说明）
- c2: 综合产物已生成（引用各子包 proof 而非复述内容）
- c3: 未决问题已列出（子包的 blocked 项 + 开放问题）
```

子包失败时父包的三选一决策（写进编译器提示词）：**重派**（调整 brief/通道再发一次，计入重试上限 1 次）/ **降级**（标记该子包 not_applicable + 在 c3 声明缺口）/ **整体阻塞**（CheckIn blocked, blockerCategory: module_waiting，等用户决策）。禁止静默吞掉子包失败。

### 3.4 上行报告合同

执行席位（SubAgent/后台任务）的返回物规格 = Matrix 上行协议：**结果摘要（≤5 行）+ 产物引用（路径/id）+ 未决问题**。大产物落文件、引用入 proof——禁止把全文结果塞回父会话上下文（token 经济）。

## 4. 与既有机制的关系

- **C4.2a 计划持久化**：steps_json 是"单 agent 顺序计划"，包树是"跨席位分派"——前者是后者的退化形态（单包多步）。编译器先判断"要不要分包"，不分包就走现有计划链路，零侵入；
- **02 裁决层**：包级 Check-in 与普通任务走同一 task-adjudicator，无特殊路径；
- **04 路由**：路由决定顶层 owner，编译发生在 owner 确定之后——两者不混；
- **09 与 11**：浏览器复合任务（"调研这个话题并整理成文档"）= 研究包 + 采集包（后台）+ 成文包，是本层的典型用例。

## 5. 工作包拆分与验收

| WP | 内容 | 依赖 | 验收 |
|----|------|------|------|
| PK1 | 包字段约定（context_refs_json 列 + packet 标记）+ 两层校验 | 02 Q1 | 迁移测试；三层嵌套被拒 |
| PK2 | 编译器提示词资产 + 触发门槛代码判定 | X3、C4.2a | direct_answer 永不分包；multi_step 产出合法包树 |
| PK3 | 执行通道查表分发 + SubAgent verbatim 注入 | PK2、I4 | 三通道各一条端到端；brief 逐字断言 |
| PK4 | 汇总包模板 + 子包失败三选一 + 上行报告合同 | PK3、02 Q4 | 子包失败 → 父包正确重派/降级/阻塞；静默吞失败 = 测试红 |

v1 范围：research 类型先行（信源调研 → 并行阅读 → 综合报告是最自然的包树），multi_step 随后。

风险：模型过度分包（把简单事拆碎）→ 触发门槛 + "一包一交付物"约束 + 包数上限（v1 ≤4）；编译器写出不可验收的 Criteria → 复用 02 模板做包级最小判据兜底。
