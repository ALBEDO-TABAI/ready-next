# 设计明细 02：任务执行质量框架（Criteria / Proof / Check-in）

> 系列：docs/agent-evolution/（00 为路线图总览）
> 来源：Matrix 调研系列 03 篇（OKR/Task 状态机）+ ready 现状调研（run_meta / task_projections / run-finalizer / 稳定性合同 v3 取证）
> 状态：设计稿（未立合同）。**本篇所有设计以"不与 2026-06-10 稳定性合同冲突、只做其数据模型延伸"为硬约束。**

## 1. 设计立场

Matrix 的完整链路是 Objective→KR→Task→Criteria→Proof→Check-in。ready 不需要 OKR 上半截（用户已确认），本篇只移植下半截三件套，目的：

- **完成是被证明的，不是被宣告的**——直击 P3（行动宣告陷阱）、P4（采集终态脱钩）的判定层根因；
- **所有非成功终态有结构化分类**——blockerCategory 让"卡在 working"成为非法状态（P1 的数据层封口）；
- **每次收尾产生显式学习决策**——learningDecision 把执行经验导入 01 篇知识系统与技能体系（03 篇消费）。

与现行合同的关系：C1.1（唯一收口通道 run-finalizer）是本框架的**写入闸门**；C1.2（行动宣告守卫）是本框架的**一个特例**（零 proof 不得 done）；C2.x（事件桥）产生的后台完成通知是本框架的**一类 proof**；C3.1（采集判定单源化）是本框架"工具建议+裁决"模式的**首个实例**；C4.2b（证据化步骤判定）blocked 期间本框架以 `verify: weak` 运行，Plan P 落地后升级。

## 2. 数据模型

### 2.1 task_projections 扩列（核心改动）

```sql
ALTER TABLE task_projections ADD COLUMN criteria_json TEXT;      -- Criteria[]
ALTER TABLE task_projections ADD COLUMN proof_refs_json TEXT;    -- ProofRef[]
ALTER TABLE task_projections ADD COLUMN checkins_json TEXT;      -- CheckIn[]（追加式）
ALTER TABLE task_projections ADD COLUMN blocker_category TEXT;   -- 最近一次阻塞分类
```

```typescript
interface Criterion {
  id: string                    // c1, c2…
  description: string           // 人话："至少采集 10 条带图内容"
  status: 'open' | 'satisfied' | 'blocked' | 'not_applicable'
  verifyMode: 'strong' | 'weak' // strong=有可运行验证器（C4.2b 后启用）；weak=模型自证
  proofRefs: string[]           // 满足该项的 ProofRef.id 列表（satisfied 时必非空）
  note?: string                 // blocked 原因等
}

interface ProofRef {
  id: string
  kind: 'artifact' | 'tool_call' | 'output_file' | 'screenshot' | 'task_event' | 'message' | 'url'
  ref: string                   // 路径 / callId / taskEventId / URL
  recordedAt: string
  meta?: Record<string, unknown>
}

interface CheckIn {
  id: string
  at: string
  status: 'completed' | 'failed' | 'cancelled' | 'blocked' | 'checkpoint'
  judgment: string              // 一行裁决："62/69 项采集成功，7 项均为视频页不适用"
  blockerCategory?: BlockerCategory   // status ∈ {blocked, failed} 时必填
  nextAction?: string           // 可推进的下一步 / 续跑指引
  decisionMaker: 'system' | 'model' | 'user'
  learningDecision?: 'ignore' | 'proof_only' | 'memory_card' | 'skill_update' | 'next_task'
  learningRefs?: string[]       // memory_card/skill_update 时必填：先写文件，路径入此
}

type BlockerCategory =
  | 'user_input_missing'        // 等用户补信息/确认
  | 'module_waiting'            // 等另一后台任务/技能子进程（Matrix 的 department_waiting 改名）
  | 'external_system_failure'   // 网络/网站/provider 故障（含 429/5xx 重试耗尽 → 对接 C5.2 blocked_external）
  | 'permission_or_credential'  // 登录墙/授权/token 过期
  | 'budget_exhausted'          // 工具预算/token 预算耗尽（对接 Plan L）
  | 'business_blocker'          // 任务本身的语义阻塞（目标不存在、内容下架等）
```

不另立 `task_evidence` 表（调研中的选项 C）作为第一阶段方案——JSON 列够用、避免多表 JOIN；当 proof 需要跨任务检索时再立表（路线图阶段三再评估）。

### 2.2 不动 run_meta

run_meta 已有 status/initiator/terminal_reason/duration_ms（C0.2），保持为 run 级账本。三件套挂在 **task 级**（task_projections），理由：一个 task 可跨多个 run（checkpoint 续跑），Criteria 的生命周期与 task 对齐而非 run。

## 3. 写入协议（谁、何时、怎么写）

### 3.1 Criteria 的产生

| 时机 | 谁写 | 内容 |
|------|------|------|
| 任务创建（projection 首建） | **代码模板** | 按 task_type 预置最小判据（见 §3.2 模板表）|
| 计划阶段（C4.2a 计划持久化） | 模型 | 可在模板基础上补充任务特定判据（追加，不可删除模板项）|
| 执行中 | 模型 | 发现判据不适用 → 标 `not_applicable` + note，不允许静默删除 |

### 3.2 最小判据模板（按真实 TASK_TYPES × module 二维对齐）

⚠️ HEAD 取证（src/shared/task-types.ts）：实际枚举为 `direct_answer | short_task | multi_step_task | media_task | continuation | research`，采集/文档等是 **module/执行账本维度**而非 task_type。模板按二维键编制：

| 键（task_type 或 module 覆盖） | 最小 Criteria（代码预置） |
|-------------------------------|--------------------------|
| direct_answer | 默认免判据（纯问答零开销）。**但非逃生门**：C1.2 行动宣告守卫全局生效——被分类为 direct_answer 的轮次若出现行动宣告（"让我现在…"），视为分类错误，adjudicator 按 short_task 判据重判，零工具不得 done |
| short_task | c1: 至少一次工具调用 **或** 结构化声明"无需工具"（C1.2 守卫的数据化） |
| multi_step_task / continuation | c1: 计划内每步有完成标记或显式跳过说明（对接 C4.2a steps_json）；c2: 至少一个产物/状态变更 proof |
| research | c1: 产出报告文件；c2: 报告含 ≥N 个来源 ref |
| media_task | c1: 媒体产物文件存在且可打开 |
| module=browser（采集） | c1: 项数达标或带 S3-2 诊断的空结果；c2: 结果文件可解析；（S3 判定矩阵的事实即此处证据包） |
| module=skill（长任务） | c1: run_state.json 终态 done 且 delivery_report 存在 |
| module=document | c1: 目标文档产生 diff；c2: 范围遵循用户指定 |

落地第一步（Q2 前置）：对 HEAD 的 task_type/module 实际取值做一次穷举核对，模板键与查表函数以该核对为准——**模板键错配 = 框架落空**，列为 Q2 的验收项。

short_task 的 c1 即行动宣告守卫的数据化：steer 后仍零工具 → c1 不满足 → 不得 done。

### 3.3 Proof 的采集（全部来自现有信号，零新增埋点）

| 来源 | 现有信号 | 转换 |
|------|---------|------|
| 工具调用 | turn-engine 的工具执行结果 | 关键写类工具（文件写、消息发送、采集提交）自动追加 `tool_call` proof |
| 产物 | `recent_artifacts_json` / `skill_task_runs.artifacts_json` | artifact 写入时同步追加 `artifact` proof |
| 后台任务终态 | C2.1 TaskEventBridge 事件 | 事件带 outputs → 追加 `task_event` proof（**事件桥的事件即证据**，与 Matrix"Background task completion notifications with output files are proof refs"同构）|
| 长任务 | run_state.json 的 deliveryReportPath/sceneScoresPath | finalize 时收割为 `output_file` proof |

### 3.4 任务裁决层 task-adjudicator（独立模块，finalizer 只调用不实现）

⚠️ 设计修正（Codex 评审第 3 点采纳）：**finalizer 是收口通道，不是验收官**。裁决逻辑独立成 `task-adjudicator.ts`（纯函数核心 + 薄 IO 壳），finalizer 在写完 run_meta 终态后调用它——否则 finalizer 会膨胀成新的中心耦合点，违背 C1.1 把它做"窄通道"的初衷。

```typescript
// task-adjudicator.ts —— 唯一的裁决实现
adjudicate(input: {
  outcome: RunOutcome                    // finalizer 传入
  criteria: Criterion[]                  // 读自 projection
  proofs: ProofRef[]
  verdictSuggestion?: DomainVerdict      // 如 S3 的采集 verdict 建议+证据包
}): { checkIn: CheckIn; criteriaPatch: Criterion[]; finalStatus: TaskStatus }
```

职责切分：finalizer 管"run 终结了、按什么 initiator"；**adjudicator 管"任务算不算完成、阻塞归哪类、学了什么"**（§3.5 完成硬规则、verdict 建议的采纳/否决、learningDecision 校验全在这里）。复合任务的包级裁决（09 篇）走同一个 adjudicator，无特殊路径。

**写入点仍只有两个**：
1. finalizer → adjudicate() → 追加 CheckIn（映射：`done→completed`、`error→failed(+blockerCategory)`、`cancelled→cancelled`、`preempted/interrupted→blocked(按 initiator 推导)`、`checkpoint→checkpoint(+nextAction=continuationRef 摘要)`）；
2. UI 交互点（用户裁决）→ 同样经 adjudicate()（decisionMaker:'user' 分支）落库。

CI gate 新增 `check-checkin-funnel.cjs`：`checkins_json` 写入只允许出现在 task-adjudicator.ts；adjudicate() 调用只允许出现在 run-finalizer.ts 与登记过的 UI handler。

### 3.5 完成判定规则（硬规则，由 task-adjudicator 实现；finalizer 只传 outcome 不判完成）

```
status 可置为 done 的充要条件：
  ∀ criterion: status ∈ {satisfied, not_applicable}
  ∧ ∀ satisfied criterion: proofRefs 非空
  ∧ proof_refs_json 至少一条
否则：
  有 proof 无裁决       → interaction_state 置 check_in_pending（新枚举值），进待裁决队列
  有 blocker            → blocked + blockerCategory
  占位值/TBD 类内容     → 视为 blocker（user_input_missing），绝不算 proof
```

"工具建议 + 裁决确认"模式（Matrix keyResultDecision 的移植）：C3.1 的 `resolveCollectionVerdict()` 纯函数输出**建议 verdict + 证据包**（计数、空轮原因、失败清单），作为 `verdictSuggestion` 传入 adjudicator 裁决——代码不再直接拍板 completed，杜绝 `no_new_content→complete` 类武断。

## 4. 待裁决队列与唤醒（轻量版 Matrix 唤醒优先级）

新增 `check_in_pending` 后，下一轮用户消息或自动续跑（C2.3/C2.4）的预处理顺序固定为：

```
1. 有 pending_task_events    → 先收割为 proof 并裁决（C2 链路）
2. 有 check_in_pending task  → 先对照 Criteria 裁决再接新需求
3. 有 blocked task 且阻塞类别为 user_input_missing → 向用户提一次性问题
4. 正常处理新输入
```

这是 Matrix 六级唤醒序的前三级裁剪版（去掉 OKR 相关的 5/6 级），以 system reminder 形式注入（复用 system-reminder-registry，新增 `pending-checkin-reminder`）。

## 5. 学习闭环（连接 01/03 篇）

### 5.1 准入门槛：学什么、不学什么（防低质卡刷屏）

`learningDecision` 默认值是 `proof_only`；选择 `memory_card`/`skill_update` 必须满足**准入四条之一**（写进 adjudicator 校验与提示词资产）：

1. **稳定偏好**——用户对同类输出的反复要求或纠偏（≥2 次同向信号）；
2. **可复用流程**——下次同类任务能直接套用的步骤/参数/站点特征；
3. **反复纠偏**——同一错误第二次出现（第一次失败默认只留 proof）；
4. **明确事实**——用户陈述或来源可证的持久事实（含站点卡，11 篇）。

**不进长期记忆**：普通任务流水（"今天完成了 X"）、一次性项目细节、单次失败、第三方网页内容的断言（只能作为带 source 的低置信候选进隔离区，03 篇）。不满足准入 → adjudicator 把 memory_card 降级为 proof_only 并在 judgment 注明。

### 5.2 执行规则

- `memory_card`：**先**调 `memory_write_card`（01 篇工具，新卡默认落 `status: staged` 隔离区）写卡，**后**把卡路径放进 learningRefs——顺序强制，杜绝"记了账没落盘"。**learningRefs 与 staged 的关系（明确规则）**：① learningRefs 指向的就是 staged 卡文件——CheckIn 的有效性只取决于"文件已落盘"，**不**取决于晋升；② 该卡进入注入的时机 = 晋升为 active 之后（01 §3.3 状态机），晋升者 = 用户采纳 / 维护任务二次信号 / 用户对话明示三者之一，CheckIn 本身不晋升；③ 卡被驳回/过期不回写 CheckIn（裁决记录是历史，不随记忆变动）；
- `skill_update`：写技能目录下的 SKILL.md/manifest 修订（用户技能）或生成"技能改进建议"卡（嵌入式技能不可写），路径进 learningRefs；
- `next_task`：创建后续 task projection，id 进 learningRefs。状态值使用 HEAD 现有枚举中的待执行态；**当前枚举若无对应值，由 Q1 迁移合同显式新增 `scheduled` 并同步 shared wire 契约与 UI 状态映射**（不得隐式引入新枚举值）；
- 03 篇 Crystallize 的 Survey 阶段把 `learningDecision ∈ {memory_card, skill_update}` 的 CheckIn 作为最高优先级信源。
